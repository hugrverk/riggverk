# WordPress WooCommerce

Prefer WordPress and WooCommerce APIs, hooks, filters, and template overrides over brittle patches.

## Process

1. **Inspect context.**
   - Identify whether the task touches theme, plugin, WooCommerce template, hook/filter, REST endpoint, admin UI, frontend assets, or content.
   - Identify classic vs block theme and shortcode vs block cart/checkout before choosing extension points; hooks and template overrides differ between them.
   - Read relevant PHP, templates, SCSS/CSS, JS, and existing hooks before editing.
   - Check existing text domain, naming patterns, asset pipeline, and verification commands.
   - Do not assume WooCommerce markup or hooks without inspecting the current version and local overrides.

2. **Choose the correct extension point.**
   - Prefer hooks and filters for behavior changes.
   - Prefer template overrides when markup structure must change.
   - Prefer enqueue APIs for assets.
   - Prefer REST/AJAX handlers only when a server interaction is required.
   - Do not modify WordPress core or WooCommerce plugin files.

3. **Implement securely.**
   - Sanitize input before storing or using it.
   - Escape output at render time.
   - Use nonces for form submissions and AJAX.
   - Check capabilities before privileged actions.
   - Use prepared queries for custom SQL.
   - Validate file uploads and never trust request data.
   - Keep public copy translatable with the project text domain.

4. **WooCommerce guardrails.**
   - Preserve cart, checkout, account, product, variation, price, stock, and tax behavior unless the task explicitly changes it.
   - Be careful with hooks that affect purchasability, variation selection, totals, shipping, or payment.
   - For product UI changes, verify simple products, variable products, out-of-stock states, and mobile behavior when relevant.
   - For template overrides, keep compatibility notes clear.

5. **Frontend integration.**
   - Reuse existing design tokens, SCSS partials, components, and breakpoints.
   - Avoid CSS-only patches when markup or hook placement is the root cause.
   - Keep JS small and scoped.
   - Respect accessibility: labels, focus states, keyboard behavior, contrast, and reduced motion where relevant.

6. **Verify.**
   - Run the narrowest relevant checks available.
   - Prefer existing repo commands.
   - For PHP, run syntax checks or project verification if available.
   - For assets, rebuild CSS/JS if source files changed.
   - For WooCommerce flows, list manual route checks such as product, shop, cart, checkout, and account when relevant.
   - State what was not verified.

## Output

- WordPress/WooCommerce area touched
- Extension point used
- Files changed or proposed
- Security/i18n considerations
- Verification run
- Remaining risk

## Guardrails

- Do not modify core or vendor plugin files.
- Do not skip sanitization, escaping, nonces, or capability checks where relevant.
- Do not break WooCommerce purchase flows for visual changes.
- Do not claim browser or checkout verification unless actually run.
- Do not broaden a theme fix into plugin architecture unless needed.
