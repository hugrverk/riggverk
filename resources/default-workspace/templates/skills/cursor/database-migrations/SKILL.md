# Database Migrations

Works across Postgres/Supabase, SQLite, MySQL, WordPress/WooCommerce databases, and common ORMs.

Done when: migration, backfill, and rollback paths are stated, and DB execution state (generated, applied locally, applied remotely) is reported without guessing.

## Do Not Use When

- The work is purely application code with no database behavior change.
- The task asks for a long ORM tutorial.
- The only path is manual production editing; stop and ask for a safer tracked change path.

## Process

1. Identify the database engine, migration tool, ORM/plugin conventions, and deployment environment.
2. Inspect existing migration style before adding or editing anything.
3. Ensure every schema change is represented as a migration or explicit tracked change.
4. Treat deployed migrations as immutable:
   - Do not edit already-applied production migrations.
   - Fix mistakes with a new forward migration.
5. Separate schema migrations from large data backfills:
   - Schema migrations should be short and predictable.
   - Backfills should be resumable, bounded, observable, and safe to rerun when possible.
6. Prefer expand-contract for risky changes:
   - Add nullable/default-safe fields first.
   - Deploy compatible app code.
   - Backfill.
   - Add constraints or remove old fields after reads and writes have moved.
7. Check compatibility:
   - Old code running with new schema.
   - New code running before all data is backfilled.
   - Rollback or redeploy behavior if the app version changes.
8. Check constraints and defaults:
   - Avoid adding `NOT NULL` or restrictive constraints before data is valid.
   - Prefer safe defaults only when they are semantically correct.
9. Check index and lock risk:
   - Large tables, concurrent index support, table rewrites, full scans, foreign keys, unique constraints, and transaction duration.
10. Check data integrity:
   - Ownership, tenant boundaries, references, cascading behavior, timestamps, soft deletes, and audit needs.
11. Define rollback and restore:
   - Code rollback path.
   - Forward fix path.
   - Backup/restore or point-in-time recovery expectation when destructive changes are possible.
12. Stop and ask before running any migration against a non-local database, or applying destructive DDL (drop, rename, type narrowing) without backup evidence.
13. Report DB execution state explicitly:
   - DB push before running this slice: YES/NO/UNKNOWN.
   - Migration generated: YES/NO.
   - Migration applied locally: YES/NO.
   - Migration applied remotely: YES/NO.

## Output

- Database scope.
- Migration files or tracked changes.
- Expand-contract or direct-change rationale.
- Lock/backfill/index risk.
- Rollback/restore plan.
- DB push and migration status.
- Commands run and results.
- Not verified.

## Guardrails

- Do not encourage manual production DB edits.
- Do not claim a migration was applied unless the command was run and reported.
- Do not mix large data backfills into schema migration files unless the stack explicitly requires it and risk is accepted.
- Do not print connection strings.
