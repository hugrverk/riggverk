# Prototype

Done when: each comparison criterion has evidence per variant, one direction is recommended, and delete-or-absorb is done or ticketed.

## When to diverge

Only create multiple variants when the direction is genuinely unclear. For simple feasibility tests, one approach is sufficient.

## Pick a branch

Identify which question is being answered from the prompt, the surrounding code, or by asking when the user is reachable:

- **Logic or state model** ("does this state machine or data model hold up?"): build the logic as a small pure module with no DOM, `document`, or handlers, and drive it from a thin throwaway shell. Prefer a single self-contained file the user can open and click through.
- **UI** ("what should this look like?"): host the variants inside an existing page behind a `?variant=` search param, so real layout, data, and density surround them. Add a throwaway route only when no existing page can host the variants, following the project's routing convention and naming it as a prototype.

If the question is ambiguous and the user is unavailable, choose the branch that matches the surrounding code (backend module: logic; page or component: UI) and state the assumed branch at the top of the prototype.

## Process

1. **Define the decision question.** What must be learned? Example: *Which layout handles overflow better for long status messages?*
2. **Define comparison criteria** before building. Examples: render time, keyboard reachability, scroll handling, developer ergonomics.
3. **Build variants** (two or three materially different) only if the question requires it. Keep copy, data, and functional requirements identical across variants.
4. **Surface the full relevant state** after every action (logic) or variant switch (UI) so changes are visible; capture tradeoffs.
5. **Recommend one direction.** Absorb only selected ideas into the production path; a validated pure module can be lifted in as is.
6. Delete unused prototype code. Do not create a permanent variant system.
7. End with a delete-or-absorb follow-up.

Boundary: prototype code lives in a clearly named throwaway directory or file. It is never imported by production modules.

## Output

- Decision question and the branch used.
- Comparison criteria.
- Files or commands used.
- Tradeoffs between variants.
- Recommended direction.
- Delete-or-absorb follow-up.

## Guardrails

- Do not let prototype shortcuts leak into production code without review.
- Do not add durable storage, migrations, long-lived config, or external services unless that is the prototype target.
- Do not present unverified prototype behavior as production evidence.
- Do not require multiple variants when a simple feasibility test answers the question.
- Keep variants wired to stubs, not real mutations.
