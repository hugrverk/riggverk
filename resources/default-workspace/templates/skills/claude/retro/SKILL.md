# Retro

Improve the agent's environment (steering files, checks, tooling, information access) from evidence in one session. Do not touch the code the session was about.

Done when: ranked proposals are presented, each traced to a session moment, and nothing has been applied.

## Scope

- Session: the one the user names; default to the current conversation. Read only that session's primary sources; never scan all logs or transcripts on the machine.
- Redact: replace secrets, tokens, passwords, cookies, and auth headers with `<REDACTED>` in anything you quote, and quote only the lines that carry the signal. If a moment cannot be shown without a credential, describe it instead.
- Propose only. Apply nothing without explicit approval of that specific proposal. Package-manager files, lockfiles, CI, build config, and environment files are edited only on explicit request.

## Process

1. Read the session's primary sources: the conversation, commands and tool results, diffs, and the steering files that were loaded (rules, AGENTS.md or CLAUDE.md, skills).
2. Look for candidates in these categories, and skip any without evidence:
   - Navigation: the agent was slow to find files or missed a hidden dependency. Propose a navigation pointer: one line in a steering file naming the doc or entry point.
   - Unwired checks: a mistake an automated check could have caught. Read the repo's own check commands first (package scripts, Makefile, CI workflow, hook config), so an existing but unwired or silently broken check is the finding rather than a new tool. A repo with no guardrail at all is itself a finding.
   - Mechanical violations: a fixed pattern (banned API, import shape, file location) calls for a deterministic check such as a lint rule, hook, or CI job, not prose. Only judgement calls (cross-file consistency, matching surrounding style) belong in a project rule read at review time.
   - Steering-file pruning: large global or repo steering files. Move content to checks or on-demand docs, and delete any sentence that fails the no-op test (does it change behavior versus the default?). Use `context-budget` for a broad audit.
   - Tool economy: expensive or noisy tool calls (unbounded output, repeated full builds, token-heavy CLI or MCP results) that a flag, wrapper, or bounded command would streamline.
   - Information access: information the agent needed but could not reach (dev-server logs, read-only access to a service, docs). Propose a way to expose it.
3. Assign enforcement to the right stage: implementation carries the most context pressure, while review sees only a diff. Standards enforcement belongs to review (the `inspector` agent or `/code-review`), not to the implementing agent.
4. Rank candidates by effect on future runs against the cost and risk of applying them.

## Output

A ranked list, highest value first. Each proposal states:

- Category and the one-line change.
- The session moment it traces to (turn, command, or file) with redacted evidence.
- Target file or command, and the expected effect.
- Cost and risk, including whether it touches package, CI, config, or environment files.

End by asking which proposals to apply; edit nothing until the user approves specific ones.

## Guardrails

- Do not propose a change without a traceable session moment.
- Do not quote credentials, tokens, cookies, auth headers, or private URLs.
- Do not rewrite steering files wholesale; propose the smallest edit per finding.
