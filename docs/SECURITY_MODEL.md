# Security Model

## Core principles

- **Writes go only to the allowlisted paths below.** The app may read the complete contents of an allowlisted Codex, OpenCode, Cursor or light-harness MCP, rules, or backup file locally when it must parse, compare, preserve, validate, merge, or restore it. Only documented keys, named entries, or the managed rules block are modified; unrelated user-owned values are preserved or cause a safe refusal with zero mutation.
- **Writes are explicit.** Install or Update shows an artifact-level plan (create, update, remove, conflict rows) and writes only after the user presses `y`. Uninstall and rollback show a preview or dry run and ask for confirmation. Library saves write only the selected personal doc (`docs/context/<slug>.md`) or the text below the managed block of an enabled harness's rules file; bundled items are read-only in the Library. Settings are an app preference and autosave. Nothing is written on launch; the removal of old workspace copies left by earlier releases is part of the reviewed `workspace` update, never run at launch. The app bundle is replaced only by an update the user reviewed.
- **Confirmation trusts the webview.** Confirmation happens in the app's own UI, so the backend cannot distinguish a user's press from script running in the webview. It enforces the reviewed plan of Install, Update, Uninstall, take bundled, the Codex config reset and a skill import with a fingerprint or digest and a one-time token, and every write with allowlisted paths, target toggles, backups and conflict refusal. A rollback takes only the transaction id, with no token from its dry run, so script in the webview could undo the last transaction without the review; the digest checks, conflict refusal and the rule on newer transactions (see Backups) still apply. Script is kept out by a CSP that allows script only from the app's own sources (inline styles are allowed), a markdown renderer without raw HTML, and capabilities limited to window and event permissions.
- **Target toggles gate Install.** A surface whose target toggle or harness is off is excluded from preview, apply, and status; the backend rejects it even if a stale request names it.
- **No credential use by the app.** The app does not authenticate with, intentionally extract, log, transmit, or expose credential-like values. Allowlisted config files and their backups can contain such values because complete bytes may need to be preserved and restored; that data stays local and is read only for bounded parsing, comparison, merge, and rollback.
- **No remote control.** The app accepts no remote commands, webhooks, or external IPC. It does run the user's installed CLIs with fixed arguments (see Scripts), and what those programs do is theirs: `opencode models` may refresh OpenCode's provider catalog over the network. No telemetry, no analytics, no cloud service, no AI model.
- **One network request, and only with consent.** The only network request the app itself makes is the update check: an HTTPS GET of `latest.json` from the Riggverk GitHub releases, made from the backend, never the webview. It runs only after the user turned on "Check daily" or chose Check for Updates; until the user answers the one-time question nothing is requested. It sends no app version, settings, paths or identifier; GitHub sees the IP address and a `tauri-plugin-updater` user agent. Offline, an automatic check fails quietly.
- **Updates are signed and explicit.** An update is downloaded only after the user reviewed its notes and pressed Download and restart, and only the version that was reviewed is installed. The archive must carry a minisign signature from the Riggverk release key, bound to the announced version (`requireSignedVersion`); otherwise nothing is changed. Only the app bundle is replaced; the workspace, rules, skills, settings and backups are not touched. Older versions are not installed by the app. A download that receives nothing for 30 seconds is given up, with nothing changed. An install waits for no apply: it is refused while one runs, and unsaved Library or settings changes are settled first, as when the window closes.
- **No unrelated credential surfaces.** The app does not inspect `.env` files, private keys, browser profiles, sessions, trust databases, keychains, or personal files outside the surfaces below. The one read of harness settings is the read-only security posture check, which looks at named keys only (see Security posture check (read-only)).

Rules files are read in full (up to 4 MB) to locate the managed block. Only the bytes between the BEGIN and END markers are written; text outside them is preserved byte-for-byte, and a file with malformed markers, a diverged pre-block file, or an edited block is refused with zero mutation. The only explicit exceptions are the user-confirmed rules conversion, which previews the exact resulting file and runs as a backed-up transaction, and a Library save of the user's refinements, which writes only the bytes after the END line and proves before writing that the BOM, the text above BEGIN and the block are unchanged; its errors and results never carry file text. Backups copy the whole file, so user text in a rules file is stored in the backup root like any other backed-up target. The "leave as is" choice is stored as non-secret identities in `<workspace>/.riggverk/rules-preferences.json`.

The Codex `config.toml` can hold MCP entries with tokens, so the "use Riggverk's defaults" reset (`preview_codex_config_defaults`, `apply_codex_config_defaults`) is the one other action that overwrites a value of the user's in it, and it never carries file text. The preview shows only the names and values of the differing enforced keys (approval and sandbox settings, a value cut at 120 characters) and a diff built from those lines, not from the file; errors are fixed phrases (a failing merge script's output is dropped), and nothing is logged. It runs through the single apply owner like `apply_take_bundled`: `apply_codex_config_defaults` plans again from disk, compares the fingerprint (the plan fingerprint, the digest of the installed file and the digest of the exact content to write), validates the one-time token (bound to the workspace, the fingerprint and the `codex_config` surface) and calls `apply_planned_artifacts`, which consumes the token once, backs up `config.toml`, records the manifest, checks the write and can roll it back. It holds the mutation lock and uses the workspace write check; it refuses when the `codex_config` target is off. The destination goes through the same resolver, allowlisted root and symlink checks as Install (a link in the file or its folders refuses before any read), and the file is read through one helper at preview and at write time (a regular file, checked before and after the open to be the same file with no link at the path, at most 1 MiB, the read bounded whatever the file grows to), as UTF-8 and parsed as TOML in the app before any script runs; untrusted content reaches the merge scripts, which run from the bundled root, only as a path argument and are the ones an update already uses. The rendered file is parsed again and compared with the installed one key by key, and refused unless the reset keys hold the bundled values, kept keys their kept values, every other enforced or create-only key that is set is unchanged (an absent one may only be added with the bundled value), the legacy profile selector and tables are removed only in the app-shipped shape, and nothing else changed. The render runs in a new owner-only temporary folder (0700, created exclusively, files 0600) and the atomic writer creates its temporary file owner-only before it holds any content. The writer writes exactly the previewed content with the same no-follow, in-root atomic write as Install, and only while the file still has the digest the preview read; otherwise it fails before the write and the transaction rolls back. The kept entries of the reset keys are removed from `config-preferences.json` afterwards. The repository guard `scripts/check-managed-installation-contract.py` forbids any other token consumption site.

A skill or agent file that differs from the bundle is a conflict the update never overwrites. The conflict diff reads the installed file and the bundled one, each only up to 512 KiB, never through a symlink, and compares text only: a non-UTF-8 or NUL-containing file is shown by size and digest, and a file with a private-key block on either side is withheld by the backend (the diff text never leaves it). The diff payload is the only carrier of file text, only for the open review; errors, logs, the status, the output pane and manual steps carry counts, labels and short digests, never a byte of a file. The UI masks credential shapes in the diff (private keys, Authorization and Cookie headers, signed-URL parameters, GitHub, OpenAI and JWT tokens) before rendering it, but not `name=value` text. Keeping the user's version records the choice in `kept-files.json` and writes no skill or agent file; handing it back deletes the choice. Taking the bundled version is the one action that overwrites a skill or agent file of the user, and it is a backed-up transaction like any update: `preview_take_bundled` is read-only and issues a one-time token bound to a fingerprint of the exact digest of every file it shows; `apply_take_bundled` plans again from disk, compares the fingerprint, validates the token and applies through the single apply owner (which consumes the token once, makes the backup, records the manifest, and checks and can roll back every write). It selects only the resolvable files of the named units (regular files with no symlink in their path, at most 64 MiB each because the backup reads the file into memory), and the writer refuses unless the artifact is a skill or agent file, its path is free of links and the file still has the reviewed digest; the write is the same no-follow, in-root atomic copy used by Install. A refusal happens before any backup or write. The user's file stays recoverable from the backup. No log, status, output or manual step carries file text: a preview carries labels, backup names and short digests, and the diff text only in the open review. The repository guard `scripts/check-managed-installation-contract.py` requires the command to apply through the apply owner and forbids any other token consumption site.

The MCP files of the light harnesses are read in full (up to 1 MiB) as strict JSON, to find and compare the one entry. They are not the app's: the other servers can hold tokens in `env` or `headers`, so their values are neither scanned for credentials, shown nor logged, and a message about a file carries a fixed reason ("the file has comments", "the file starts with a byte order mark", "the top level of the file is not an object") and never a byte of its text. Only the bundled entry template is scanned for credential-like literals before it is written. A file is refused with zero mutation when it is not UTF-8, starts with a byte order mark, has comments or a trailing comma, is not a JSON object at the top, or holds the servers key as something other than an object; so is an entry named `playwright` that is not the managed one (it is the user's own, unless a record proves the app wrote it and it is unchanged since). A write replaces the file with the user's keys in their order and the entry inserted or replaced: indentation is normalized to two spaces, a final newline is added, duplicate keys collapse to the last, and numbers follow serde's formatting (an integer beyond 64 bits would be written as a float); every other value is kept. The write is atomic, an existing file keeps its permission bits, and a new file is created 0600. Backups copy the whole file, so a backup of an MCP file holds whatever secrets the user keeps in it; backups are owner-only (0600, folders 0700) in the backup root like any other backed-up target. Uninstall never deletes an MCP file.

Claude's `~/.claude/settings.json` is read in full (up to 1 MiB) as strict JSON while the `claude_config` target is on, to see whether `attribution.commit` and `attribution.pr` are set. The rest of the file (`env`, `hooks`, `permissions`, ...) is the user's: the setting does not scan it (the posture check below reads only its named keys), it is never shown or logged, and a message about it carries a fixed reason (the same phrases as for the MCP files, or "attribution has an unexpected type") and never a byte of its text. The refusals are the MCP file's (not UTF-8, byte order mark, comments, trailing comma, not an object, over 1 MiB, not a regular file), plus an `attribution` that is neither an object nor `false`. Values the user set (one key, custom text, `attribution: false`, `includeCoAuthoredBy`, or both keys `""` with no ownership record) are left as they are and never recorded as the app's. A write replaces the file with the user's keys in their order and the two values inserted: indentation is normalized to two spaces, a final newline is added, duplicate keys collapse to the last, and numbers follow serde's formatting (an integer beyond 64 bits would be written as a float). The write is atomic and an existing file keeps its permission bits. Backups copy the whole file, so the backup holds whatever secrets the user keeps in `env`; backups are owner-only (0600, folders 0700) in the backup root like any other backed-up target. Undo puts the two keys back as the backup had them and keeps every other edit made since. Uninstall never deletes the file. The Claude health check never opens it.

App support and backup roots are platform-resolved:

| Platform | App support dir | Backup root |
|----------|-----------------|-------------|
| macOS | `~/Library/Application Support/se.hugrverk.riggverk` | `<app support>/backups` |
| Linux | `${XDG_CONFIG_HOME:-~/.config}/se.hugrverk.riggverk` | `<app support>/backups` |
| Windows | `%APPDATA%\se.hugrverk.riggverk` | `<app support>\backups` |

On Linux an `XDG_CONFIG_HOME` that is relative, `/`, or holds a `..` is ignored and `~/.config` is used, as for the OpenCode and Kilo folders. Backup roots reject `/`, the home directory, and drive roots.

The app support dir is named like the bundle identifier. Builds from before the Riggverk rename used an older name. On first launch, before anything reads or writes app data, the app moves that directory to the current name with a single rename in the same parent folder: nothing is copied or deleted, and contents, modes, and modification times are preserved. The current directory wins when it already exists (the two are never merged), and an old path that is a symlink or not a directory is never followed. A failed move stops startup with both paths named and leaves the old directory where it was. [RELEASE.md](./RELEASE.md#app-data-move) has the details and the manual undo.

On Windows, skill-pack and setup-backup trust checks reject symlinks and junctions on the checked entry and its ancestors through the trusted root; other reparse points, such as OneDrive cloud placeholders, are allowed. They do not inspect Windows ownership or ACLs; private file and directory modes (0600/0700) are no-ops there, so privacy relies on the profile and destination ACLs set by Windows. Cross-instance mutation locking uses a non-blocking standard file lock; closing the handle or process exit releases it. Atomic replacement retries sharing-violation (32) and access-denied (5) errors up to five attempts, with 20, 40, 80 and 160 ms delays between attempts. Other replacement errors are returned immediately.

## Security posture check (read-only)

The `security` group of a harness page reads a few named keys of that harness's global config (`get_security_posture`, `src-tauri/src/commands/security_posture.rs`). These files can hold provider keys, so the read is bounded and leaves nothing behind: one read of at most 1 MiB, parsed in memory, reduced to booleans, enums and counts, and dropped. The result type holds only fixed codes, levels, static file names and counts; parse errors are mapped to a unit value without formatting (TOML errors quote their source), and the module has no print or log call. A test per file type plants a marker in a secret position, in a comment and on a broken line, and requires that it is absent from the serialized result. The check writes nothing, does not read `.env` files, and does not run any CLI.

| Harness | File | Keys read |
|---------|------|-----------|
| Claude Code | `~/.claude/settings.json`; skipped while `CLAUDE_CONFIG_DIR` is set | `permissions.defaultMode`, `permissions.disableBypassPermissionsMode`, `permissions.deny` (only whether a `Read` rule names `.env`), `sandbox.enabled` |
| Codex | `$CODEX_HOME/config.toml` | `sandbox_mode`, `approval_policy`, `sandbox_workspace_write.network_access`, `projects.*.trust_level` (counted) |
| OpenCode | `opencode.json`, `opencode.jsonc`, `config.json` | `permission`, `permission.bash`, `permission.read` (counted `deny` actions) |
| Cursor | `~/.cursor/sandbox.json` | `type`, `networkPolicy.default` |
| Kilo Code | `kilo.jsonc` or `kilo.json` | `permission`, `permission.bash` |

It sees global config only. Project and managed config, profiles, command-line flags and aliases can change what a harness does and are named in the page as not checked; the page never says secure. Copilot, Pi, Antigravity and Grok are reported as not covered without reading anything.

## Backups

Existing files that Install, uninstall, or a Library save would overwrite or remove are backed up first. Files that do not exist yet, the app's own `settings.json`, the window state, and the model override have no backup.

| Writer | Location under the backup root |
|--------|--------------------------------|
| Install, uninstall, rollback | `setup/<transaction id>/` with `manifest.json`, `artifacts/<artifact id>`, and `managed-state.previous.json` |
| Library save (personal doc) | `docs/custom_<slug>-<timestamp>/<file>` |
| Library save (rules refinements) | `docs/rules-<surface>-<timestamp>/<file>` |
| Library save (personal pack skill) | `docs/pack_personal_<name>-<timestamp>/SKILL.md` |
| Skill import (replace, remove, undo) | `imports/<name>-<pid>-<nanos>/<name>/` (the whole skill folder) |
| Cursor operations (and the retired CLI scripts) | `<YYYYMMDD-HHMMSS>/<label>/<file>` |

The app creates backup directories 0700 and files 0600 on Unix (mode settings are no-ops on Windows), with one exception: `pack-skills.previous.json` (pack and skill names only) gets the default mode for new files, inside its 0700 transaction folder. Backups that releases before v2026.10.1 left 0644 (folders 0755) are tightened once per app run, before its first setup transaction: group and other permission bits are removed from everything below the backup root, links and entries on another file system are skipped, and failures are ignored. Backups are read locally for validation, comparison, and rollback only and are never transmitted. Rollback restores exact prior state from a persisted transaction: per-artifact `in_flight` is recorded before mutation, interrupted rollbacks reconcile against post-apply and backup digests without overwriting unrelated user edits, and conflicts fail closed. The manifest and the backed-up bytes are not authenticated: their digests are trusted because only the user can write them. So rollback and interrupted-transaction recovery refuse a transaction whose folder, `manifest.json` or `artifacts/` folder is a link or (on Windows) a junction, is not owned by the current user, or is writable by its group or by everyone (Unix), and refuse to restore a backup file (or any file or folder of a folder backup, and the pack-skills record backup) that fails the same checks, each with a fixed-phrase reason and no restore. Windows ownership and ACLs are not checked. Only write access counts on Unix: backups that releases before v2026.10.1 left 0644 (folders 0755) still restore. A backup root on a shared or synced volume is outside this model. The in-app rollback entry (`z`, `:rollback`) covers the last transaction of the current session.

Installation mutations are serialized in the trusted Rust backend: every write command, settings saves and the workspace reset included, holds one process-wide mutation lock, and an exclusive advisory file lock on `mutation.lock` in the app data folder for as long as it runs (`flock` on Unix and the standard file-lock API on Windows). A second app instance (`open -n`, a dev build on the same profile) is refused with "Riggverk is busy in another window" instead of reconciling the first one's running transaction as interrupted. This holds only while the lock file is usable: when it cannot be created or opened, is not a regular file, or cannot be locked for a reason other than another holder, the command runs with the in-process lock alone. Every mutating setup command rolls back interrupted transactions of the workspace before it checks the preview's fingerprint and token, so a plan approved before that reconcile mismatches and is previewed again. Undo of a transaction is refused while a newer transaction of the workspace is not rolled back (completed, rollback failed, or unfinished), because its managed-state snapshot would erase the newer one's records. Packaged resources and runtime destinations are resolved separately and must never be the same root. Bounded copy and removal helpers require an explicit allowlisted root, reject dangling destination symlinks, and validate parent chains before creating or removing trees. Preview confirmation tokens are opaque, one-time, in-memory, expire after 600 seconds, and must not appear in logs or diagnostics.

OpenCode agent permissions are composed from `templates/opencode.policy.json` plus small `templates/opencode/agents/*.role.json` overrides. Restrictive roles use explicit `composition.replace_sections` so bash/edit profiles replace inherited capability sections instead of shallow-merging them. Shared secret denials remain canonical in the base policy and are emitted for the worktree root as well as nested paths, because OpenCode matches worktree-relative paths. The policy's `builtin_agents` section becomes managed `agent.plan.permission` and `agent.explore.permission` entries in `opencode.json` that keep OpenCode's built-in read-only agents read-only under the global permission block. Generated `agents/*.md` adapters are deterministic outputs; edit sources, not generated headers. `scripts/validate_opencode_permissions.py` enforces the semantic permission contract in release-check, evaluating bash rules per command of a compound like OpenCode; `resources/default-workspace/docs/OPENCODE_CONFIG.md` lists what the rules cannot see (the `grep` tool, a redirect behind a second command).

## Skill packs

`<workspace>/packs/<pack>/skills/...` is a second, user-controlled source of skill files, read like the bundle's: bounded (64 files and 2 MiB per skill, four levels), never through a symlink or Windows junction. The app writes only its own two packs, `personal` (Library copies and saves) and `imported` (Skill import, below); it never writes, repairs or removes anything in any other pack. A pack skill without `targets` is for every harness Riggverk supports (the key is Riggverk's, not the Agent Skills spec's); a target it names must be a known one. A pack that is a symlink (or Windows junction), holds a symlink below `skills/` (or Windows junction), or (Unix) has its folder, `skills/` or anything below it writable by its group or by everyone, or owned by someone else than the current user, is refused as a whole (and `packs/` itself fails the same checks for every pack). Windows ownership and ACLs are not checked. A pack skill reaches the skills folders only through the reviewed, backed-up Install, with the same proof of ownership as any file (a managed record or an exact byte match); an edited installed copy is a conflict the app never overwrites, and the bundle wins every name collision. A pack grants no capability the user did not already have: they can write `~/.claude/skills` and `~/.agents/skills` directly, and a pack is only a way to keep those files under Git and have them installed, updated and rolled back with the same guarantees. Pack text is shown in the Library as text and is never executed by the app; the scripts a skill carries run only when a harness runs them, as for any skill in those folders. Treat a pack like any repository you take skills from: a cloned pack is code your agent will follow.

A pack skill's `SKILL.md` is copied byte for byte, frontmatter included, and some frontmatter keys make the harness act without the model choosing to or without a prompt: in Claude Code, `allowed-tools` lets the listed tools run without asking while the skill is active, and command `hooks` are registered when the skill is invoked and run for the session; `context`, `agent`, `background` and `model` change where and how the skill runs. The body can act too: Claude Code runs `` !`command` `` (and a ```` ```! ```` block) as a shell command when the skill loads, before the model reads the text, and `allowed-tools` can pre-approve it. The Library renders a skill's body without its frontmatter, so for a pack skill it lists each of these keys with its value (whitespace collapsed) in the metadata block, `allowed-tools` marked "grants tool access without asking" and `hooks` "runs commands without asking", plus a `!` entry naming every body line with a `` !` `` command or a fence of three or more backticks or tildes followed by `!`, "runs shell commands when the skill loads". The Install review gives such a skill a row of its own in every skills folder it creates or updates, with the pack, the keys and their values (and the `!` lines) (each cut at 200 characters; the Library shows it whole). These keys are shown, never refused: a pack is trusted like any repository you take skills from, and the user can write the same files directly. Frontmatter that a YAML parser could read differently from the app is refused instead, so no key can be set without being listed: a top-level entry that is not a plain `key: value` line (an explicit `?` key, a tag, an anchor or alias, a `<<` merge key, a flow collection, a byte order mark), or a `SKILL.md` that anywhere holds a lone carriage return, U+2028, U+2029 or a control character other than tab. Such a pack skill shows as an error and is neither installed nor updated. The values are config, not secrets, and are shown as written. Bundled skills set some of these keys too (see the bundle's `docs/SKILLS.md`); they are reviewed where the bundle is built and are not listed.

A pack's `routing.md` adds lines to the managed block of every rules file the app writes, so its text reaches the instructions of every enabled agent, not only those that load the pack's skills. That is the same trust as the pack's skills, which already become agent instructions, and the same reader enforces it: the file is read only from a pack that passed the checks above, must itself be a regular file that is no symlink and (Unix) owned by the current user and not group- or world-writable, and is capped at 12288 bytes and 60 lines of at most 240 characters. Only `- ` bullet lines are accepted, with no `<` (no HTML or marker comment that could end the block early), no heading, no code fence and no control or invisible character (zero-width, bidi override, tag, variation selector and the other default-ignorable code points; Unicode Cf, Zl, Zp and more), and every backticked name must be an active skill of that same pack, so a pack cannot route agents to a bundled skill or to another pack's. Any violation excludes the whole file, with a fixed-phrase reason in the Library that quotes none of its text; nothing is ever applied in part. The app writes only `packs/imported/routing.md`, from the "Use when" text in the import or routing dialog, which shows the exact line before it is saved. A suggestion taken from the imported skill's own description is filled in and ticked, so it is untrusted text: it passes the same checks, and the line, the rules diff of the next Update and its undo are where the user reviews it. Removing an imported skill removes its routing lines. The app never writes another pack’s routing file. Nothing is written to rules files when the routing file changes: the next Install shows the rules files as updates, with the added and removed lines in the preview diff, and writes them only after review, with a backup and undo like any base update.

## Skill import

Skill import (Library → Packs → Import skill…) copies a skill the user found elsewhere into `<workspace>/packs/imported/skills/<name>/`, the app-owned pack `imported`. It reads only the paths the user dropped onto the window or typed: Tauri hands the webview the dropped paths (no content), using the event permission the app already has (`core:event:allow-listen`); there is no file dialog plugin, no zip reader and no network access. For GitHub the dialog only shows a `git clone <url> ~/.config/riggverk/packs/<name>` command for the user to run.

- **Preview.** `preview_skill_import` takes the mutation lock, finds the skills (the folder itself, a loose `SKILL.md`, or `<name>/SKILL.md` and `skills/<name>/SKILL.md` of a folder; at most 16 paths, a limit of 64 on the skills found, 2,000 entries looked through), and checks each with `lstat` only, before anything is copied. The folders above the chosen path are resolved once (they are what the user named; macOS's `/tmp` is a link), and the preview shows and the record keeps that resolved path; a link at the chosen path itself or anywhere below it is refused: no symlink (never followed), no hard link (`nlink > 1`), no device, socket or pipe, no nested `SKILL.md`, at most 256 entries, the pack limits (`SKILL.md` 1 MiB; 64 supporting files, 2 MiB in all, 1 MiB each, four levels) and names the installer can represent. Dot entries are skipped and listed. A skill that passes is copied into `<workspace>/.riggverk/import-staging/<token>/` (folders 0700, files 0600, or 0700 for a source file with an execute bit, which stays executable in the pack and when installed); each source file is opened without following a link and without blocking (`O_NOFOLLOW | O_NONBLOCK`), and the opened handle is refused unless it is a regular file with one link and still the device, inode and size the scan saw. The copy is then validated: UTF-8 `SKILL.md`, frontmatter read as the pack reader reads it (a key given twice refused, as is the frontmatter the Skill packs section above refuses), `name` and `description` present, `name` by the spec's rule (`^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64) and equal to its folder's name, known `targets` if any, the pack reader's support-file checks on the copy itself, Unicode tag characters (U+E0000–E007F) and bidi overrides and isolates (U+202A–202E, U+2066–2069) refused, and the other characters a routing line refuses as invisible (format characters, variation selectors, Hangul fillers and the like) flagged with their count and lines, except a presentation selector U+FE0E or U+FE0F right after a visible non-ASCII character, which only picks how that character looks. Supporting files are not scanned for these characters. A name a bundled skill has is offered a rename; a name of another pack's skill is refused, and no import is checked while a pack is refused or ignored. The preview returns the manifest (files, sizes, executable bit, binary, names that cannot be installed), the flags (the privileged keys and `!` lines of Skill packs above, `agents/openai.yaml`, scripts and executables, binary files, hidden Unicode), the raw `SKILL.md`, a SHA-256 tree digest, a per-file diff against an import of the same name, and a one-time token (the preview-token registry: opaque, in memory, 600 seconds) bound to the digest of the staged manifest. Refused skills are not kept in staging, and each preview removes the staging of the earlier ones, so it holds one preview at most. The source path is compared after resolving links: the packs and state folders cannot be a source. Every entry counts against the 256, dot entries included, and no more are listed. The names in the import record are checked before use (a record changed by hand that names something else is not used), and a backup is found only under the label the app gave it.
- **Commit.** `commit_skill_import` takes the mutation lock, checks the token against the staged manifest, re-reads every picked staged copy and the import in place and refuses when either differs from the preview, then spends the token. It checks every name again and publishes each skill from staging: written into a dot-named temporary folder in `packs/imported/skills/`, then put in place with `rename`; an import in place is first copied into the backups (`imports/<name>-…/`), moved aside, and removed only after the record is written. A rename rewrites only the one top-level `name:` line of the frontmatter: the dialog shows that line as a diff and the whole text as it will be written, and the commit derives the same bytes from the verified staged text and the new name and refuses when anything else would differ (a `SKILL.md` without a plain `name:` line is not renamed). The record `packs/imported/.riggverk-imports.json` (dot-named, so never read as a skill; written atomically) keeps per skill the source as `~/...`, the kind of source, the time, a SHA-256 per file and the tree digest, plus an event per import, replacement, removal and undo (the last 200). A record that cannot be read is never rewritten: imports stop until it is fixed.
- **Remove and undo.** `remove_imported_skill` copies the skill into the backups, then removes it from the pack; since only the app writes `imported`, a skill gone from it (even its last one) is retired by the next Update like any skill removed from a present pack, with a backup. `undo_last_import` takes back the latest event not yet taken back: an import or replacement only while the skill is still what it published (its tree digest), backing the current copy up first; a replaced or removed copy comes back from its backup, only when the backup passes the same trust check as a setup rollback (no link, and on Unix owned by the current user and not writable by its group or by everyone) and its tree digest equals the recorded one.
- **Library.** Imports are read-only; "Edit as my copy" (`copy_skill_to_pack` with a `pack:imported/<name>` id) copies an active import into `packs/personal/`. Each imported skill shows where it came from.

What never happens:

1. The app runs anything of a skill: a script, a hook, a `!` command, an installer or a URL.
2. An import writes into an agent's skills folder. Only the reviewed Update all installs, with a backup and undo.
3. A write outside `packs/imported/`, the staging folder and the backups; a link followed in the source; a path from a skill (its file names are checked by the same rules as an installed skill's, so no `..` and no absolute path).
4. Anything published that the preview did not show, or a half-copied skill visible in the pack.
5. The bundle, another pack or an edited installed copy overwritten: names are refused, and the Update review keeps its conflict rules.
6. A flag hidden, shortened without saying so, or dropped.
7. An update in the background or without a new preview and diff.
8. A network request, a credential in a URL, telemetry, or an upload to a scanner.
9. Permanent deletion: a replaced, removed or undone import goes into the backups.
10. Skill text interpreted as HTML: the preview shows `SKILL.md` as text, and the Library's renderer has no raw HTML.
11. A badge or word that says a skill is verified or safe.

## Symlinks

Managed writes (Install, uninstall, rollback, backups) reject symlinked targets, symlinked parent chains, and dangling symlinks. Skill discovery rejects symlinked skill roots, groups, and directories. Library reads of bundled items (documents, rules template, skills, agents, configs) come from the app's bundle, never from a copy in the workspace, and enforce containment in the bundle and refuse symlinks. Personal docs are read from the workspace's own `docs/context` under the same checks; Library writes go only to a file directly in it and refuse a symlink on the file, the folder, or a parent; the personal doc listing skips symlinks. The cleanup of old workspace copies removes only a regular file with no symlink on it or on a folder above it, below the data folder; anything else is left in place. A Library save of rules refinements refuses a symlinked rules file or a symlinked folder between it and its allowlisted root, and reads the file only when it is a regular file; `o` may open a symlinked rules file, which the OS follows to where it lives.

These are checks made before each step, not a race-free guarantee: a managed write, copy or removal checks the path and then acts on the path again, without holding the folder open, so someone who can already write the user's config folders could swap a folder for a link in between. Skill import reads its sources differently: it opens each source file without following a link and checks that the opened file is the one it scanned.

## Git

The app runs no `git` command. It does not read the Git state of the data folder or of any project, and it never fetches, pushes, or contacts a remote. A repository in the data folder is yours to manage.

## Scripts

The app runs its `python3` merge and generator helpers from the copy bundled with the app, never from the data folder, with `-I` and fixed arguments. It never uses `sh -c` or a shell plugin (`check-shell-spawn.py` enforces this in release-check). Both the Codex merge scripts and the OpenCode generator look for `python3` in the Homebrew and per-user bin folders first and then on `PATH` (a Finder launch puts macOS's own `/usr/bin/python3` first on `PATH`). On Unix a candidate is run only by its resolved path, and only when it and its folder are owned by the current user or root and not writable by group or others; any other candidate is skipped. The OpenCode generator runs on the first candidate that passes, any version, and fails with a fixed phrase when none does. The Codex config merge scripts also need `tomllib` (Python 3.11+): their interpreter is the first passing candidate that passes `python3 -I -c "import tomllib"`, probed once per process. Without one, a Codex config update is a conflict at preview and an Undo that must merge the file back is refused in its preview, both with the fixed phrase "Python 3.11 or newer is needed to update the Codex config. A python3 that someone other than you or root owns or can write, or whose folder they can write, is not used."; nothing fails mid-transaction. The output of a merge script or of the OpenCode generator check never reaches an error or a status: they can quote lines of the user's config, so failures are fixed phrases. Parse errors of the user's `config.toml`, `opencode.json` and `mcp.json` are fixed phrases too (TOML errors quote their source line).

The OpenCode Runtime and Model cells also run the installed `opencode` CLI: `--version`, `debug agent <default_agent> --pure` and `models` (`--pure`, or `--standalone` on OpenCode 2.x). The binary comes from `PATH`, `/opt/homebrew/bin`, `/usr/local/bin` or `~/.opencode/bin`, never from the workspace; unlike `python3`, it is not checked for ownership. Arguments are fixed, except the default agent name, which must start with a letter or digit and is passed as one argument. Each call has a timeout and an output cap and runs from a new owner-only (0700) folder in the app data folder, removed afterwards, with `OPENCODE_DISABLE_PROJECT_CONFIG=1` set: OpenCode reads `opencode.json` and `.opencode/` from the working directory and every folder above it. `opencode models` may refresh OpenCode's provider catalog over the network. Only the exit status, a version number and `provider/model` ids are kept; raw output is not stored or logged.

OpenCode runtime health reads the installed `opencode.json` as JSONC (comments and trailing commas, as OpenCode does) for the comparison only; install still writes strict JSON and leaves a JSONC file untouched. It also parses `config.json` and `opencode.jsonc` in `~/.config/opencode` (regular files up to 1 MiB) and keeps only the names of the managed keys they set. Of the process environment it keeps the names of the set OpenCode config variables (`OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT`, `OPENCODE_PERMISSION`, `OPENCODE_DISABLE_PROJECT_CONFIG`, `OPENCODE_DISABLE_CLAUDE_CODE*`); values are only checked for being empty. Of the system managed config (`/Library/Application Support/opencode` and the `ai.opencode.managed` managed preferences on macOS, `/etc/opencode`, `%ProgramData%\opencode`) only path existence is checked. Warnings and rows carry fixed phrases, file names, key names and variable names, never file text or values.

The pages of the light harnesses (GitHub Copilot, Pi, Kilo Code, Google Antigravity, Grok Build) run only `<cli> --version`, for `copilot`, `pi`, `kilo`, `agy` and `grok`. The program is found on `PATH` or, for these five only, as `bin/<name>` of the highest version folder below `~/.nvm/versions/node` (nvm's alias files are not read); the app puts that folder, which holds `node`, in front of the probe's `PATH`. The argument list is fixed and the program names come from an embedded descriptor, never from the workspace; the program is not checked for ownership. The call has a 10 second timeout and a 4 KiB cap per output stream and runs from a new owner-only folder in the app data folder, removed afterwards; only the version token is kept, and raw output is not stored or logged. No other subcommand is ever run: `copilot version` asks the network, `pi --help` and `kilo debug paths|config` create files in the harness's own folders, and `kilo debug config` prints the resolved config with its secrets. Apart from the rules, MCP and skills files in the table above, nothing in `~/.copilot`, `~/.pi`, `~/.config/kilo` or `~/.gemini` is written (Antigravity's `antigravity-cli/settings.json`, `antigravity/mcp_oauth_tokens.json` and `config/agents/` included), and nothing is read but the Kilo config file the posture check reads (`config.json`, `settings.json`, `auth.json`, `models.json`, sessions and the like are never opened, and the descriptor refuses them as targets). For Kilo, whether `opencode.json`, `opencode.jsonc` (beside the chosen file) and `~/.kilo/kilo.json[c]` exist is checked, to warn that they win over the entry; they are never opened. No MCP subcommand is ever run: `pi mcp list` starts the configured servers, `kilo mcp` and `kilo debug config` print the resolved config with its secrets and create files, and `copilot mcp` is not needed. The health rows show statuses and counts, never file text. The effective-load view opens the `SKILL.md` of the skills below `~/.copilot/skills`, `~/.pi/agent/skills`, `~/.kilo/skills`, `~/.grok/skills` and Antigravity's two folders, like it does for the other harnesses' skills folders. In `~/.grok` only `config.toml` is written and read (parsed whole in memory to edit one table; only the managed entry is kept); `auth.json`, sessions and agents are never opened. The community `superagent-ai/grok-cli` installs a program of the same name; Grok Build documents no `--version` output that tells the two apart, so the page does not try.

## What the app does NOT access

- `.env` files or arbitrary secret environment values. The app reads documented operational variables (workspace, backup, Codex home, skill roots, Playwright, XDG, `HOME`, `PATH`); their values must not be printed or persisted as user content.
- Private keys, cookies, or credential stores.
- Browser profiles, bookmarks, or saved passwords.
- System keychains, SSH agent state, or GPG state.
- IDE authentication state, tokens, sessions, or trust databases.
- Unrelated IDE settings or MCP server payloads outside the allowlisted Playwright entries of Cursor and of the light harnesses (the other servers in those files are parsed with the file and never scanned, shown or logged).
- Project `.git/` directories.

## App updates

The app has an updater (`src-tauri/src/app_update.rs`, `tauri-plugin-updater`) that is on: `src-tauri/tauri.conf.json` has a `plugins.updater` block with the release key's public key (minisign key ID `9EEAB656BE9922F4`), the GitHub `latest.json` endpoint and `requireSignedVersion: true` (docs/RELEASE.md, "Turning on updates"). Without that block the plugin is not registered, the app menu has no Check for Updates, the UI shows no update card or setting, and the app itself makes no network requests. A block that names a key and an endpoint but turns on a `dangerous*` option, allows downgrades, uses plain HTTP or leaves out `requireSignedVersion` counts as off, in the app (`app_update::configured`) and in `release.sh` (`release_tools.py updater-config`). The webview never gets the plugin's commands: no capability names them, so checks and installs run only through the app's own Rust commands, and the CSP does not change. A check is given up after 10 seconds, and a download is given up when no bytes arrive for 30 seconds (the wait restarts with every read, so a slow download still finishes), with "The download failed. Nothing was changed." The release notes in `latest.json` are not covered by the signature: the review renders them as markdown without raw HTML, with only http(s) and in-page links, and the CSP blocks remote images. `release.sh publish` reads the release key and its password from the maintainer's Keychain into the environment of the one `tauri build` that signs the archive; no other release step gets them, but every build script of that build runs with them (docs/RELEASE.md).

## Process output

Command output shown in the app is redacted: private-key blocks, Authorization and Cookie headers, values of secret-named keys and well-known token shapes are masked. A subprocess's output is read up to at most 16 MiB of stdout and 512 KiB of stderr; some calls set lower caps. Every helper script, CLI probe and macOS `open` call has a timeout (120 s unless the call sets another), and a timeout kills its whole process group (`taskkill /T` on Windows). The opener on Linux and Windows is the exception: `xdg-open` and `explorer.exe` are left running once they have run for 3 seconds, since they can stay in the foreground with what they opened; macOS `open` has the 120 s timeout. `open`, `xdg-open`, `explorer.exe` and `taskkill` are found by name on `PATH`, with no ownership check.

## Release verification

`scripts/release-check.sh` validates source format, templates, adapter currency, and contracts. It runs apply smokes against temporary `HOME` directories and never writes the real user config. See [RELEASE.md](./RELEASE.md).
